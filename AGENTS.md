# AGENTS.md

Living roadmap and architecture-decision log for the AI captioning/video-editing app. Update the checklist and decisions log at the end of every step — this is where "why we built it this way" lives, as opposed to `CLAUDE.md` which only documents how to run the repo as it exists today.

## Product roadmap

- [x] **Step 1 — Upload → transcribe → caption editor.** Upload a video, extract audio with ffmpeg, transcribe with Deepgram (word-level timestamps, punctuation, filler words, numerals, language auto-detect), group words into caption-sized cues, and show a video-editor-style screen: transcript editor on the left, Remotion `<Player>` preview (video + burned-in caption overlay) on the right. Edits save back to MongoDB.
- [x] **Step 3 — caption styling.** Preset style gallery (from `backend/data/caption-styles.json`) + custom style creation in a right-hand sidebar, a 9-position picker, a Line/Word/Balanced display-mode toggle, and an editable "Full text" paragraph view alongside the per-cue "Captions" view. (Step 2 below is still open — done out of order because the user asked for styling next.)
- [x] **Step 5 — export.** Server-side Remotion render (`@remotion/renderer`, reusing the exact same `CaptionedVideo` composition as the live preview) to produce a downloadable MP4 with burned-in captions at the source's original resolution. Plus Reset-settings and Upload-another-video actions. (Also done ahead of Step 2, same reason as above.)
- [x] **Step 4 (partial) — AI Highlight.** Groq (`openai/gpt-oss-20b`) picks out the "main" words/phrases from the stored transcript on demand (button in a new "AI Highlight" tab), cached on the `Transcript` doc so it's only ever generated once per video. Matched words render prominently (user-configurable color/background/bold) everywhere captions render — live preview, every style, and the export. Also resolved the Split Emphasis gap below as a side effect. Custom caption styles are now editable/deletable from the sidebar, not just creatable. The rest of Step 4 (punctuation cleanup, filler trimming, clip suggestions) is still open.
- [ ] **Step 2 — richer caption editing.** Drag-to-resize individual word/cue timing boundaries, split/merge cues, speaker labels, undo/redo.

## Architecture decisions

- **Sync processing (Step 1).** Upload → ffmpeg → Deepgram → Mongo all happen inside one `POST /api/videos` request/response. No job queue yet. Revisit with a background job + status-polling endpoint if uploads get large/slow enough that a single HTTP request isn't a good fit.
- **Audio extraction picks the smaller of mp3/opus.** `backend/src/services/ffmpeg.js` extracts mono 16kHz audio as both `libmp3lame` (mp3) and `libopus` (ogg), keeps whichever file is smaller, and sends that to Deepgram. Shells out to the system `ffmpeg`/`ffprobe` binaries directly (`child_process`) rather than adding `fluent-ffmpeg`.
- **Cue segmentation is our own heuristic, not a Deepgram feature.** `backend/src/services/cues.js` groups Deepgram's word-level timestamps into caption-sized cues (breaks on word count, pause length, or sentence end). This keeps us in control of cue boundaries for future re-timing/splitting/merging (Step 2), rather than depending on Deepgram's `paragraphs` feature.
- **Deepgram params:** `model=nova-3`, `punctuate=true`, `filler_words=true` (default on — easier to delete unwanted words in the editor than to recover stripped ones), `numerals=true`, plus either `language=<code>` or `detect_language=true`. See `backend/src/services/deepgram.js`.
- **`frontend/src/remotion/*` uses inline styles, not Tailwind classes.** Verified via DOM inspection that `@remotion/player`'s `<Player>` does *not* render in an isolated iframe (0 iframes, `<video>` sits directly in the main document) — so Tailwind classes would actually work here. Inline styles are still the right call because the composition needs to be portable to server-side rendering in Step 5 (`@remotion/renderer` / `npx remotion render`), which runs in a separate headless-Chromium context that won't automatically have the Vite app's Tailwind stylesheet loaded. Also uses `<Video>` from `remotion`, not `<OffthreadVideo>` (that's for server-side rendering).
- **No router library yet.** Only two screens (upload, editor); `App.tsx` toggles between them with local state. Revisit once there are more than ~2-3 routes.
- **Port 5000 is unusable for the backend on this machine** — macOS's ControlCenter/AirPlay Receiver squats on it. Backend runs on **5001** (`backend/.env` `PORT`); the frontend Vite dev server proxies `/api` → `http://localhost:5001` (`frontend/vite.config.ts`).
- **`<Player>` `inputProps` must be a stable object reference.** `EditorScreen.tsx` was passing a fresh `{ videoUrl, cues }` object literal every render; since `currentTime` state updates on every `frameupdate` event during playback (many times/sec), this recreated the object constantly, which made the Player re-sync/reseek the underlying `<video>` and caused visible stutter/repeated-word/backward-jump playback. Fixed by wrapping it in `useMemo(() => ({ videoUrl, cues }), [videoUrl, cues])`. Any future prop passed to `<Player>` should get the same treatment — don't inline object/array literals there. It now also carries `words`/`style`/`position`, all included in the `useMemo` deps.
- **Caption styles live in Mongo, seeded from a JSON file inside `backend/`.** `backend/data/caption-styles.json` holds the preset definitions (schemaless `config` per style, since presets vary wildly — chromatic aberration, typewriter reveal, karaoke highlight, letterbox bars, rotate+shadow, dash-prefix are all one-off fields on top of the common font/color/box fields). `syncCaptionStyles()` upserts every entry (by `name`) into the `CaptionStyle` collection on server startup, and de-dupes same-name entries within the file itself. Because the file lives inside `backend/` and nodemon watches that whole tree, editing/appending to it triggers a restart → automatic re-sync. It never deletes — removing an entry from the file leaves an orphaned Mongo doc; delete it manually (or via `DELETE /api/caption-styles/:id` if `isCustom`) if that matters.
- **Custom styles join the same library as presets** (`isCustom: true`), so they show up in the style sidebar for every video, not just the one they were created on. The custom-style *creation form* only exposes core fields (font/size/weight/style/color/background/padding/radius/box-shadow/uppercase) — the exotic per-preset effects below are preset-only, not user-composable.
- **"Full text" tab stays structurally per-cue.** It's a stack of borderless, auto-growing (`field-sizing: content`) `<textarea>`s — same controlled value/onChange wiring as the "Captions" tab — styled with no borders/timestamps so they read as one flowing paragraph. This was a deliberate choice over a single free-text box: editing a single flattened string would require re-splitting text back into cues on save, which risks desyncing word-level timestamps. Both tabs edit the exact same `cues` state, so they're always in sync.
- **Caption rendering (`frontend/src/remotion/Captions.tsx`) supports the full effect set from `captions.json`, not just core styling:**
  - Position is a 9-way grid (`top/middle/bottom` × `left/center/right`), independent of whichever style is selected — picking a style never changes position, and vice versa. A preset's own `position` field (e.g. `"bottom"`, `"above-bottom-bar"`) is stored but purely informational.
  - **Chromatic aberration** ("Retro VHS") renders as `text-shadow` (two colored offset shadows), not duplicate absolutely-positioned text layers — the first attempt used absolute layers and they wrapped independently from the base text, causing a visibly duplicated/overflowing line on multi-line captions. `text-shadow` doesn't have that failure mode since it's on the same text node.
  - **Karaoke highlight** ("Pop Karaoke") and **typewriter reveal** ("Typewriter") both need word-level timing, which is why `words` (not just `cues`) now flows all the way from the API response into the Remotion composition.
  - **Letterbox bars** ("Cinematic Letterbox") are rendered in `CaptionedVideo.tsx` as frame decoration (not part of the caption text box), so they stay put regardless of caption position.
  - **"Split Emphasis" gap resolved.** Now that AI Highlight provides real keyword data, `Captions.tsx` uses Split Emphasis's own `keywordColor`/`keywordWeight` for highlighted words instead of the generic user highlight settings — that's clearly what those fields were for. Non-highlighted words still fall through to `baseColor`/`baseWeight` via normal CSS inheritance from the box.
- **Caption display modes (Line/Word/Balanced)** are computed in `Captions.tsx` as an "effective cue" transform applied *before* the existing per-style effect logic (`getEffectiveCue()`) — `word` mode swaps in the single currently-spoken word (from `words`, holding the last-completed word during pauses to avoid flicker), `balanced` mode splits the cue text into two lines at whichever word boundary best balances line length. Because every style effect (karaoke, typewriter, chromatic aberration) just operates on whatever cue/text it's given, this composes for free — no per-style special-casing needed for display mode.
- **Investigated but not fixed: a reported "style edit doesn't apply until you switch styles and back" bug.** Could not reproduce across three different fresh-browser-session scenarios (different cues, different styles, typing speed, mid-playback edits) — the `cues` state → memoized `inputProps` → `<Player>` chain was verified correct each time. Most likely explanation: React Fast Refresh staleness from the many live edits pushed to `EditorScreen.tsx`/`Captions.tsx` while a tab was open during that work, not a logic bug. If it recurs after a hard refresh, get exact repro steps before assuming the same conclusion.
- **Export renders server-side via Remotion, reusing the live-preview composition.** `backend/src/services/render.js` wraps `@remotion/bundler`'s `bundle()` (memoized per server process — bundling takes a few seconds, done once) and `@remotion/renderer`'s `selectComposition()`/`renderMedia()`, pointed at a new entry point, `frontend/src/remotion/index.ts` (`registerRoot`) + `Root.tsx` (registers the `<Composition id="CaptionedVideo">`, with `calculateMetadata` reading `durationInFrames`/`width`/`height` back out of props since they vary per video). This means every style/position/display-mode effect works in the export with zero reimplementation, at the cost of a real architectural coupling: **the backend's bundler references a file inside `frontend/`'s source tree** (`../../../frontend/src/remotion/index.ts` from `backend/src/services/render.js`). Only `@remotion/bundler`/`@remotion/renderer` are backend dependencies — the entry point's own imports (`remotion`, `react`) resolve from `frontend/node_modules` via normal upward Node resolution, so no duplicate install. Revisit this coupling if the repo ever grows a proper shared workspace package.
- **Video resolution is captured at upload time** (`ffprobeDimensions()` in `backend/src/services/ffmpeg.js`, stored as `Video.width`/`height`) and used as the actual `compositionWidth`/`compositionHeight` for both the live `<Player>` preview and the export render — previously both were hardcoded to 1280×720 regardless of the source video, which would have silently up/downscaled anything that wasn't already that size. This is what makes "download without losing quality" literally true (native resolution + `crf: 18` h264, not just a high bitrate at the wrong size). Falls back to 1280×720 for any video uploaded before this field existed.
- **`@remotion/renderer` needs its own headless-Chromium download** (separate from Playwright's, cached under `~/.remotion` — no relation to `~/Library/Caches/ms-playwright`, which is only used by our own Playwright-driven browser smoke tests, not by the app itself). On this machine it downloaded at only ~200KB/s (~93.5MB, ~7-8 minutes) — a one-time cost, cached after. Don't reach for Playwright's cached binary as a shortcut here (`browserExecutable` override) — it happens to exist on this machine only because of our own testing and wouldn't exist for a real user, so it's not a legitimate fix for slow first-download UX; if that ever needs solving, it's a "show download progress" / "pre-warm on server start" problem, not a "borrow a different tool's cache" one.
- **AI Highlight uses Groq's `openai/gpt-oss-20b`** (OpenAI's open-weight model, hosted on Groq — `backend/src/services/groq.js`), `response_format: json_object`, defensive `JSON.parse` (falls back to `[]` rather than throwing on malformed output). The endpoint (`POST /api/videos/:id/highlight`) never accepts a transcript in the request body — it loads the video's own already-stored `Transcript` doc server-side. It's generated **at most once per video, ever**: `Transcript.highlightsGeneratedAt` gates the call, and the endpoint returns the cached `highlightedWords` immediately if already set. There's deliberately no regenerate button.
- **Highlight matching is string-based, not index-based.** Groq returns verbatim keyword/phrase substrings; rendering normalizes (strip leading/trailing punctuation, lowercase, Unicode-aware via `\p{L}\p{N}`) each displayed word and checks set membership. Multi-word phrases (Groq sometimes returns e.g. `"time stamps"`) get split into individual words at storage-read time, since captions render word-by-word. This means editing caption text after highlights are generated just works — a word that no longer appears simply stops matching, no invalidation/regeneration logic needed.
- **`Captions.tsx`'s "plain" rendering path (used by most presets) now always tokenizes into per-word `<span>`s** (`renderTokensWithHighlights`) instead of returning a flat string — this is what makes AI-highlighted words stylable without touching every preset individually. The karaoke ("Pop Karaoke") branch checks the highlight set per word too; its own momentary `activeColor` for the currently-spoken word still wins over the highlight look for that instant. Typewriter reveal highlights words as they're fully typed (a still-being-typed partial word won't match until the trailing space commits it) — accepted as a minor cosmetic simplification, not worth the complexity of mid-reveal word-boundary tracking.
- **Custom style edit/delete**: `PATCH /api/caption-styles/:id` (new, same `isCustom` guard as the pre-existing `DELETE`) lets `CustomStyleForm` double as an edit dialog (`initial` prop pre-fills it, submit routes to update instead of create). `StyleSidebar` shows pencil/trash icons only on custom entries, never presets. Delete confirms via a plain `window.confirm` — deliberately not a custom modal, since this only ever touches the user's own low-stakes data.
